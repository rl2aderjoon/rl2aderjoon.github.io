풀었던 문제

재전송된 이벤트가 취향에 두 번 더해졌다

원인ID를 직접 넣는 엔티티라 Spring Data가 persist 대신 merge로 저장해서, 중복 예외가 한 번도 나지 않았습니다.

접근INSERT … ON CONFLICT DO NOTHING의 영향 행 수로 판정하고, 장부 기록과 취향 반영을 한 트랜잭션으로 묶었습니다.

결과동시·순차 중복과 중간 장애 시 손실을 함께 막았고, 통합 테스트로 고정했습니다.

배치를 걷어내자 취향이 시간을 모르게 됐다

원인90일 삭제가 몰래 감쇠 역할을 하고 있었습니다.

접근매일 raw × 0.97 + 오늘 기여. 이벤트 시각을 저장하지 않아도 무게가 0.97경과일이 됩니다.

결과압축값이 아니라 raw에 곱해야 한다는 점을 테스트로 고정했습니다. 직접 고른 설문 값은 감쇠하지 않습니다.

코스 목록이 3.7초, 최장 12.8초 걸렸다

원인OR-Tools 프로세스가 한 번 뜰 때마다 약 0.45초. 3일 × 2안이면 2.7초가 반복됐습니다.

접근같은 추천 판과 요청자 기준으로 2·3안 초안을 한 번만 계산하고, 동시 요청은 future로 합쳤습니다.

결과응답 형태를 바꾸지 않고 재계산을 없앴습니다.

후보 200곳 중 199곳이 식당이었다

원인가산점이 상위 200을 독식하는 구조였습니다.

접근자르기 전에 갈래별로 몫을 나눴습니다. 고른 갈래 70%, 끼니 15%, 쉼 5%.

결과취향을 지키면서 일정의 다양성을 보장했습니다.

풀었던 문제

/odom이 9.9Hz로 떨어지고 최대 0.575초 끊겼다

접근같은 Orin에서 도는 /scan을 대조군으로 두고 비교해 Orin 과부하가 아님을 먼저 확인했습니다.

원인커밋 없이 추가된 열화상 센서 판독이 ESP32 loop()를 최대 약 570ms 막아 20Hz PID 루프를 잠식하고 있었습니다.

결과코어 분리, 판독 주기 제한, 원시 바이트 전송의 세 가지 대책을 정리했습니다.

부팅할 때마다 로봇이 다르게 움직였다

접근증상 여섯 개를 구조적 성질 네 개로 다시 묶었습니다. 기동 순서 미강제, 판정 불가 시 통과, map→odom 소유권 이중화, 조용한 실패.

원인DDS 참여자는 약 85개인데 실제 노드는 37개. 좀비 노드 정황이 있었습니다.

결과2차 시연에서는 자동화를 빼고 다섯 단계를 순서대로 기동했습니다.

전진 명령에도 로봇이 거의 움직이지 않았다

접근원시 텔레메트리에서 duty는 상한인데 엔코더는 0인 것을 확인하고, 모터 보호를 위해 시험을 멈췄습니다.

발견대시보드 슬라이더의 잔여값이 안전 상한 duty_max를 조용히 덮어쓰는 버그를 함께 찾았습니다.

결과버그는 바로 고쳤고, 원인은 물리적 끼임으로 확인했습니다.

화재·연기 탐지 모델(YOLO11, mAP50 0.790)은 팀 AI 파트가 학습했습니다. 저는 주행 영상 오탐을 줄이는 파인튜닝·평가 도구를 만들었습니다.

왜 만들었나

AI 개발 시대에는 한 사람이 에이전트 여럿을 동시에 돌립니다

문제사람 팀은 회의로 일을 나누지만, 에이전트는 서로의 존재를 모릅니다. 같은 파일을 동시에 고치고, 나중에 끝낸 쪽이 앞의 작업을 덮어씁니다.

접근고치기 전에 "이 경로는 내가 한다"를 git 안의 장부에 적게 했습니다. 서버도 계정도 없이 원격 저장소 하나로 동작합니다.

결과가볼래 6인 팀 저장소에서 사람과 AI가 한 달 동안 3,562번 선점했습니다.

충돌을 머지 때가 아니라 시작 전에 잡습니다

문제git 충돌은 둘 다 일을 끝낸 뒤에 드러납니다. AI는 몇 분 만에 수백 줄을 쓰기 때문에, 늦게 알수록 버리는 작업이 커집니다.

접근경로가 겹치면 시작 전에 거부합니다. 겹침 판정은 LLM이 아니라 경로 파서가, 동시 기록은 git ref CAS가 맡습니다. git 3-way 머지에 판정을 맡기면 같은 입력도 장부 상태에 따라 결과가 갈려서 버렸습니다.

결과멈춘 세션의 선점은 45분 뒤 저절로 풀리고, 커밋 훅이 선점하지 않은 경로의 커밋을 검사합니다.

회사가 다른 모델끼리 대화시킵니다

문제모델마다 잘하는 일이 달라서 한 작업에 섞어 씁니다. 조율은 Claude, 서버는 Codex, 영상 실험은 Gemini처럼요. 그런데 각 도구의 대화 기능은 자기 회사 세션끼리만 통합니다.

접근axMap이 회사와 상관없는 우체국 역할을 합니다. 세 도구 모두 같은 MCP 도구로 선점하고, 쪽지를 보내고, 작업을 요청합니다.

결과에이전트끼리 1,345통의 쪽지를 주고받았고, 합의 표는 484번 기록됐습니다.

쪽지를 보내도 토큰을 아낍니다

문제AI는 메시지를 받을 때마다 새로 생각을 시작하고, 그때마다 지금까지의 대화 전체를 다시 읽습니다. 제 기록으로는 응답 한 번에 평균 37만 토큰입니다. "진행 중", "확인했어요" 같은 알림 하나도 그만큼의 비용을 씁니다.

접근일반 쪽지는 모델을 부르지 않고 받은 편지함에 쌓아 둡니다. 받는 쪽은 테스트나 실험이 끝난 시점에 한 번에 회수합니다. 같은 사람이 같은 주제로 다시 보내면 최신 한 통만 남기고, 단순 알림에는 답장을 금지했습니다. 바로 끼어드는 건 중단 요청, 데이터 손실, 지금 작업을 무효로 만드는 변경 세 가지뿐입니다.

결과쪽지가 여러 통 와도 받는 쪽 AI가 새로 생각을 시작하는 건 회수할 때 한 번입니다.

회사가 달라도 대화가 바로 이어집니다

문제다른 회사 세션에 일을 맡기면 새 대화를 열어야 해서, 그동안 쌓인 맥락이 사라졌습니다. Windows에서는 agy 화면을 한 번 읽을 때마다 도우미를 새로 컴파일했습니다.

접근같은 PC 안의 대화는 git을 거치지 않고 Named Pipe·Unix socket으로 직접 전달합니다. 이미 켜진 Codex 대화에 새 대화를 만들지 않고 그대로 이어 붙여서, 이전 맥락을 기억한 채 답하게 했습니다. 화면 도우미는 한 번만 컴파일해 재사용합니다.

결과요청 접수 0.31~0.44초, 답을 받기까지 5.2~6.2초이고 대부분은 모델이 생각하는 시간입니다. agy 화면 읽기는 618ms에서 127ms로 4.85배 빨라졌습니다.

충돌을 몇 번 막았는지는 측정하지 않았습니다. 거절 기록이 장부에 남지 않기 때문입니다. 쪽지 묶음으로 실제 아낀 토큰과, 같은 회사 세션끼리의 대화와 비교한 속도도 아직 측정하지 않았습니다. 시간 수치는 Windows 한 대에서 잰 값입니다.

풀었던 문제

AI 추천이 이미 많이 오른 종목만 골랐다

진단추격 편향이 들어오는 경로 세 곳을 코드에서 찾았습니다. UP 1차 필터, 빈 값일 때 가중치 재분배, 기대 상승률 2차 정렬.

재설계52주 고점 대비 하락, 장기 이동평균 재안착, 저점을 높이는 채널, 돌파일 거래량 같은 일곱 가지 매수 기준.

정직하게과거 시점 데이터가 없는 산업·재무 기준은 백테스트에서 뺐다고 밝혔습니다.

목표에 닿지 못하면 어떻게 하나요?

왜 닿지 못하는지를 숫자로 보고합니다. 로보터블 프로젝트에서는 F1 85% 목표에 대해 사후 상한 72.3%를 계산해 구조적으로 어렵다는 근거를 냈습니다.

가볼래 음식 랭킹 평가는 Recall 기준에 못 미쳤지만, 모델이 맛이 아니라 관광 안내를 배우고 있었다는 사실을 확인하고 문서로 남겼습니다.

AI 코딩 에이전트는 어떻게 쓰나요?

여러 에이전트를 동시에 돌리면서 생기는 덮어쓰기 문제를 직접 겪었고, 그래서 axMap을 만들었습니다. 6인 팀 저장소에서 한 달 동안 3,562번의 선점이 이 도구로 오갔습니다.

에이전트에게 맡기더라도 설계 판단, 검증 기준, 실험 규약은 제가 정하고 결과를 원본에서 직접 확인합니다.

하드웨어도 다룰 수 있나요?

삐용에서 차체를 파라메트릭 CAD로 설계해 3D 프린팅했고, 무납땜 전원 배선과 ESP32 속도 PID 펌웨어를 맡았습니다. 엔코더 CPR, 바퀴 지름, 트레드를 실측해 한 문서를 기준으로 삼았습니다.

느린 API는 어떻게 고치나요?

먼저 시간을 어디서 쓰는지 잽니다. 가볼래 코스 목록은 OR-Tools 프로세스 기동이 반복되는 것이 원인이었고, 응답 형태를 바꾸지 않고 재계산만 없앴습니다. 삐용 카메라 노드도 인코딩 경로를 바꿔 CPU를 4.3배 줄였습니다.
